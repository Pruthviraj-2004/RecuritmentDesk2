# Architecture

RecruitmentDesk is a **modular monolith**: one FastAPI application, one Celery worker image (same code), PostgreSQL, Redis, and a static React SPA. There are no microservices.

```
Browser (React SPA, same-origin /api)            Google (OAuth 2.0, Gmail API)      AI provider (OpenAI-compatible)
        │  HttpOnly session cookie + CSRF header            ▲                                ▲
        ▼                                                    │                                │
  nginx / Vite proxy ──► FastAPI (/api/v1) ──enqueue──► Redis ──► Celery worker ───────────────┘
                              │                                      │  (sync, extraction, export, send)
                              └────────────► PostgreSQL ◄────────────┘   Celery beat: periodic sync, resume, cleanup
                                              + private file storage (exports, extracted attachment text)
```

## Backend layout (`backend/app`)

| Package | Responsibility |
|---|---|
| `core/` | settings + startup validation, security (argon2, Fernet, PKCE, rate limiter), structured logging with secret redaction, typed errors |
| `db/`, `models/` | SQLAlchemy 2 models (portable: PostgreSQL in production, SQLite in tests), UTC-aware timestamps |
| `integrations/` | `gmail_client.py` (Google OAuth client + Gmail gateway on Google's official library), `storage.py` (private local storage) |
| `services/gmail/` | account connection + token lifecycle, MIME parsing, attachment parsing, sync engine |
| `services/classification/` | deterministic rule-based classifier and field hints |
| `services/extraction/` | provider interface (`AIProvider`), OpenAI-compatible provider, schema, evidence validation, per-message pipeline |
| `services/normalization/` | Unicode/whitespace, HTML→text, titles, companies, locations, skill aliases, fingerprints |
| `services/deduplication/` | matcher: deterministic rules first, weighted similarity second |
| `services/requirements/` | create/edit with versioning, ingest-with-dedup, merge, filtering/search |
| `services/candidates/` | candidate create/update + duplicate detection, CSV/XLSX importer (template, header aliases, validation, dry run), deterministic candidate-requirement matching, Excel export |
| `services/candidates/ai_profile.py` | AI profile agent: prompt, schema with salvage, grounding against the source text, calculated tenure analytics, apply-to-record |
| `services/exports/`, `services/delivery/` | openpyxl workbook generation; Gmail send with idempotency and uncertainty handling |
| `tasks/` | `runner.py` (task bodies + dispatcher), `celery_app.py` (retry/backoff, beat schedule) |
| `api/v1/endpoints/` | thin HTTP layer: validation, authorization, response shaping |

## Request flow and authorization

1. `get_ctx` resolves the HttpOnly session cookie → server-side session (only a SHA-256 of the token is stored), checks expiry/revocation, enforces the **CSRF header** on non-safe methods, loads the user's organization and role.
2. `require_role(viewer|member|admin|owner)` guards each route. Every query is filtered by `organization_id`.
3. Handlers call services, commit, and then **enqueue** background work (so workers never see uncommitted rows).

## Background processing

* `enqueue()` sends to Celery when `REDIS_URL` is set; otherwise (tests, no-Redis dev) it runs the task inline. Task bodies are plain functions that open their own DB session.
* **Idempotent**: messages are unique on `(email_account_id, gmail_message_id)`; requirement ingestion is idempotent per source message; export/delivery tasks no-op if already completed.
* **Resumable**: sync jobs checkpoint `page_token` after every page in `processing_jobs.checkpoint`; the Gmail `historyId` only advances after a *complete* run. `resume_stuck_jobs` (beat, 5 min) re-dispatches jobs with no heartbeat for 10 min; `process_pending` picks up messages left pending.
* **Bounded retries**: transient Gmail/AI errors retry with exponential backoff (Celery) up to `max_attempts`, then the job is `failed` and visible. Permanent errors (revoked grant, bad AI key) never retry.
* Sends are **never auto-retried** (`max_retries=0`).

## Gmail synchronization

* Initial/full: windowed query (`newer_than:Nd -in:spam -in:trash …` **plus hiring-related search terms**), paginated, deduplicated, checkpointed. Mail generated by RecruitmentDesk itself (export header / delivery Message-ID, own-account spreadsheet digests, Sent-only mail; `services/gmail/own_mail.py`) is skipped so exports can never be re-extracted. Mail the classifier marks clearly unrelated is dropped before storage (setting `only_recruitment_emails`, default on).
* Incremental: `users.history.list` from the stored `historyId`. If Gmail reports the cursor expired (404) it falls back to a windowed reconcile and records `history_expired`.
* A daily reconcile (beat) re-reads the last 3 days to recover anything missed. Pub/Sub push is **not** required and not implemented; the config key is reserved.

## Extraction pipeline (per message)

attachments (safe parse) → rule-based classification (clear noise skips the AI) → AI extraction (JSON, schema-validated) → **evidence validation** (emails must literally appear in the source, unsupported skills are dropped, ranges fixed, confidence computed) → normalization → deduplication → persist + audit. Without an AI provider the message becomes `awaiting_ai` (not failed) and is processed once a provider is configured.

## Frontend (`frontend/src`)

React + strict TypeScript + Vite + Tailwind. Server state via TanStack Query, tables via TanStack Table (server-side pagination/sort/filter), forms via React Hook Form + Zod. Features are folders under `features/`; reusable pieces under `components/`. The session lives in an HttpOnly cookie; the CSRF token is held **in memory only**. Filter state for the requirements list lives in the URL.

## Staying under Gmail's rate limits

* **Pacing:** every Gmail call goes through one governor that spaces calls `1 / GMAIL_REQUESTS_PER_SECOND` apart (default 4/s, about 20 of Gmail's 250 quota units per second). A 1,000-message mailbox is read steadily in a few minutes instead of in a burst.
* **Backoff:** a 429 / rateLimitExceeded reply doubles the gap (up to 8x, easing back as calls succeed) and the call is retried up to `GMAIL_MAX_RETRIES` times with exponential waits, honouring Gmail's `Retry-After`.
* **Pause, not fail:** if Gmail still refuses, the sync job is paused (status queued, cooldown 5, 10, 20, 40 then 60 minutes, stored as `resume_after` in its checkpoint) and carries on from the last page when the cooldown ends. Rate limits never use up the job's retry attempts; it is only given up after 30 pauses. Already-stored messages are never fetched again.
